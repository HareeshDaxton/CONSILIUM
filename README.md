# CONSILIUM

Multi-agent **glaucoma screening support**. You upload a retinal fundus image and an
optional clinical note, and CONSILIUM returns an evidence-linked report that a clinician
reviews and signs. The report exports to PDF or Word.

```
Your laptop (CPU) — this repo                     Deva's laptop (GPU) — Deva/
──────────────────────────────────                ─────────────────────────────
Web app: upload fundus image + note
API ── image ───────────────────────────────────▶ server.py: SwinV2 + SegFormer
    ◀── P(glaucoma) + optic disc/cup masks ──────
CDR, risk tier, quality checks (in-repo code)
note de-identification → 3 isolated specialist agents (OpenAI)
→ Director draft → deterministic verifier + adversarial critic
→ report (draft) → clinician review & sign → PDF / Word
```

Design and rules: [AGENTS.md](AGENTS.md), [doc/ARCHITECTURE.md](doc/ARCHITECTURE.md).
Screening support only. It never produces a diagnosis, and a report is final only when a
clinician who did not submit the case signs it.

## Run it

**Deva (GPU laptop):** double-click `Deva/run.bat` (see [Deva/README.md](Deva/README.md)). It prints a public ngrok
URL and a token. He sends you those two lines.

**You (this laptop):**

1. Fill in `.env` (use `.env.example` as the template):
   - `OPENAI_API_KEY`: needed for the AI agents that write the report.
   - `VISION_ENDPOINT_URL` / `VISION_ENDPOINT_TOKEN`: Deva's URL and token.
   - `JWT_SECRET` (32+ random characters) and `FIELD_ENCRYPTION_KEY`.
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLINICIANS`, `GOOGLE_SUBMITTERS`: for Google sign-in.
2. Start everything:

   ```powershell
   docker compose up -d postgres
   uv run python scripts/run_app.py          # API + worker on :8000; prints vision/AI status
   cd frontend; npm ci; npm run dev          # web app on http://localhost:5173
   ```

3. Open http://localhost:5173 and sign in with Google. Then go to **New screening**:
   upload an image, add an optional note, and click **Generate report**. Watch the progress,
   read the report, and use **Download PDF / Word**.

Offline demo without Deva or OpenAI (canned AI, fake vision, seeded cases):
`uv run python scripts/dev_ui_stack.py --reset`.

## Models

Interim third-party weights (Apache-2.0, fine-tuned on REFUGE), pinned in
`configs/models.yaml` and `Deva/wire.py`:
`pamixsun/swinv2_tiny_for_glaucoma_classification` and
`pamixsun/segformer_for_optic_disc_cup_segmentation`. Because these weights were trained
on REFUGE, REFUGE cannot serve as held-out evaluation data for them. Probability
calibration is not fitted yet, and the report says so. No performance figures are claimed
anywhere until they come from stored evaluation runs (Phase 13).

## Evaluation (Phase 13)

The `eval/` harness runs the paper's four-stage ablation on a frozen case set. In S1 a single
agent sees the full context. S2 uses multiple agents with a shared context, S3 uses
multiple agents with routed contexts, and S4 adds verification (full CONSILIUM). The
recorded CAD outputs are held constant, so only the architecture changes between stages.
Each case runs at least 3 samples, results carry case-level bootstrap 95% CIs, and stages
are compared through paired per-case differences.

```powershell
make eval-smoke                 # offline, synthetic LLM: checks the harness wiring, never a result
make eval-live                  # live LLM on the frozen synthetic cases (needs OPENAI_API_KEY)
make eval-record SPEC=cases.json # freeze the full set once through the vision endpoint
make eval-full                  # live LLM on the recorded full set
make eval-report RUN=<run_id>   # every table, generated from a stored run only
```

Every run is stored once and never overwritten. It records the git SHA, config hashes,
model and prompt versions, dataset version, seed, and every per-case outcome. The block
below is generated by `python -m consilium.eval.report --run-id <id> --readme` from the run
it names. Do not edit it by hand.

## Differences from the paper

- **CDR formula.** The paper computes `sqrt(|cup| / (|cup| + |disc|))`. That is a
  cup-to-disc ratio only when the disc mask is rim-only. With the usual nested masks, where
  the disc includes the cup, it counts the cup twice and comes out too low. CONSILIUM
  reports the clinical **vertical** CDR (cup height / disc height) as the primary number.
  It also reports `sqrt(cup_area / disc_area)` as a secondary value, for comparison with the
  paper.
- **Similarity, not distance.** The paper alternates between cosine *distance* and cosine
  *similarity*. Here `S_inter` is always the mean pairwise cosine **similarity** of the
  specialist sub-reports, so higher means more convergent. The embedding is a fixed,
  eval-only lexical model (`hashed-ngram-tf@v1`), and every run records it. Because it is
  lexical, paraphrased text counts as diverse, and values are not comparable across
  embedders.
- **Real numbers.** The paper's results are qualitative, and its Figure 3 has no axis
  values. Every figure here comes from a stored run. A run on the synthetic smoke cases says
  nothing about real fundus images, and its report states that. Negative and null results
  appear in the hypothesis table next to positive ones.
- **Verification.** The paper relies on an LLM critic alone. CONSILIUM runs a deterministic
  verifier first (references, numbers, coverage, forbidden language, dissent, role scope)
  and then the LLM critic. The critic checks claims against both the CAD metrics and the
  clinical-note facts. Fault injection measures recall per layer and records every miss by
  name.
- **Memory.** V1 has no pgvector feedback memory, by design. Clinician corrections are
  stored relationally as structured data for V2.
- **Vision serving.** The models run behind a remote, pinned endpoint (`VisionClient`). All
  interpretation (calibration, tier, CDR, quality checks) happens in this repo.
- **Held-out data.** The interim vision weights were fine-tuned on REFUGE, so REFUGE images
  cannot be used for the full evaluation set of those weights.

## Observability and runbook

`docker compose --profile observability up -d` adds Prometheus (http://localhost:9090) and
Grafana (http://localhost:3001, dashboard "CONSILIUM overview"). Prometheus scrapes the API
(`:8000/metrics`) and the worker (`:9100/metrics`, `WORKER_METRICS_PORT`). Set
`OTEL_ENDPOINT` to export traces (one span per graph node, LLM call and vision call), and
set `LANGFUSE_HOST` / `LANGFUSE_PUBLIC_KEY` / `LANGFUSE_SECRET_KEY` to send LLM generation
metadata to a self-hosted Langfuse. Spans and Langfuse events carry identities and counts
only, never prompts, notes, images or model output. The alert rules are in
`deploy/observability/alerts.yml`.

| Alert | Threshold | Action |
|---|---|---|
| `VisionFailureSpike` | more than 10% of vision calls fail for 10 min | Check that Deva's server or the endpoint is up and serving the pinned revision. Roll the pin back only through a deliberate `configs/models.yaml` change. Cases fail closed meanwhile. |
| `VisionRevisionMismatch` | any mismatch in 5 min | The endpoint is serving a different model than the one CONSILIUM was tuned for. Stop and redeploy the pinned weights, or bump the pin deliberately together with thresholds and calibration (`vision-endpoint` skill). |
| `VisionColdStartSpike` | more than 0.3 retries per successful vision call for 15 min | Switch the endpoint to always-on, or raise `VISION_TIMEOUT_S`. This is a cost decision, not a code change. |
| `CriticRoundOneApprovalNear100` | more than 98% of drafts approved in round 1 over 6 h (min 20) | Possible critic degradation. Run `make eval-live` and check the fault-injection table (`critic-fault-injection` skill) before trusting new approvals. |
| `NeedsAttentionDrift` | more than 25% of drafted cases end NEEDS_ATTENTION over 6 h | Triage a sample with the `bad-report-triage` skill. The Phase 13 live run already shows critic over-rejection (S4 UNVERIFIED 1.0), so this alert is expected to fire until critic prompt v2 lands. |
| `ReviewBacklog` | more than 20 cases awaiting review (24 h arrivals minus decisions) for 2 h | Staffing, not a system change. Nothing is ever auto-approved. |
| `LLMErrorSpike` | more than 5% of LLM calls failing for 10 min | Check the provider status, `OPENAI_API_KEY` and quota, and the pinned snapshot's availability. Cases fail closed. |

## Release status (V1)

V1 is **ready for a supervised pilot on synthetic or consented research data only**. It is not ready
for real patient data until the open items in [doc/release_checklist.md](doc/release_checklist.md) are
signed. Supporting documents: [threat model](doc/threat_model.md), [backup and restore](doc/dr.md),
[load test](doc/load_test.md), [model card](doc/MODEL_CARD.md).

To freeze new submissions during an incident or rollback, set `INTAKE_FROZEN=true`. New cases then get
a 503, while review and reports keep working.
